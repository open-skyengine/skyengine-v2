# MRP 启动与执行模型

MRP 不是单一的“ARM 可执行文件”。一个包可以只包含 MR 字节码/脚本，也可以由 MR 入口启动原生 EXT，还可以由原生包装层继续装载游戏或插件模块。兼容运行时应按包内容和入口参数选择路径，不应把某一种游戏的模块层次当作格式要求。

## 典型启动链

```text
验证 MRP 头部和目录
  -> 选择包与入口文件（通常为 start.mr）
  -> 建立 Mythroad VM 和平台状态
  -> 执行 start.mr
  -> 可选：读取并解压 cfunction.ext
  -> 校验 MRPGCMAP，调用 +8 处原生入口
  -> 原生入口登记 helper 与模块参数块
  -> helper(code=0) 初始化
  -> 事件、计时器和异步结果循环
  -> 可选：装载 game.ext、graphics.ext 或其他子模块
  -> pause/resume/exit
  -> 释放模块、VM 与平台资源
```

这是常见路径，而不是包结构的强制清单。每一步都应允许明确失败和回滚，尤其是解压、原生映射、入口调用和子模块初始化。

## `start.mr`

`start.mr` 是默认的 MR 层入口名称。它由 Mythroad VM 执行，负责应用级初始化、资源装载和事件处理，也可能调用平台能力来装载原生模块。其具体字节码版本和标准库能力随 SDK 世代变化。

需要区分三种情况：

- 纯 MR 包没有 `cfunction.ext`，全部逻辑在 MR 层完成。
- 常见原生包由 `start.mr` 引导，再装载 `cfunction.ext`。
- 运行时或调用者可能指定不同入口，目录中也可能出现重名入口；选择规则不能只由容器解析器决定。

**证据：稳定 SDK ABI（默认名称）与版本/平台相关（字节码和入口选择）。**

## `cfunction.ext`

`cfunction.ext` 是常见的第一层原生包装模块，但不是所有 MRP 的必选文件。它通常承担以下职责：

- 取得宿主平台表；
- 建立本模块的 RW/静态基址；
- 向平台表槽 25 登记 helper 回调；
- 接收初始化、事件、计时器和生命周期消息；
- 在复杂应用中继续装载其他 EXT。

解压后的常见 EXT 以 8 字节 ASCII `MRPGCMAP` 开始，代码入口位于文件偏移 `+8`。入口通常称为：

```c
int32_t mr_c_function_load(int32_t code);
```

文件标记、函数名和入口协议属于互操作约定；映射到哪个虚拟地址、用解释执行还是硬件执行、如何管理宿主对象则属于实现选择。

**证据：多样本验证与稳定 SDK ABI。**

## helper 协议

原生入口通过平台表槽 25 所代表的 `_mr_c_function_new` 登记回调。常见回调类型可以抽象为：

```c
typedef int32_t (*mr_c_function)(
    void *module,
    int32_t code,
    uint8_t *input,
    int32_t input_len,
    uint8_t **output,
    int32_t *output_len
);
```

这里的 `module` 是 guest ABI 中的模块参数，不应被宿主实现解释成自己的原生指针。`input`/`output` 同样需要经过 guest 地址空间验证。

常见消息码：

| code | 含义 | 常见数据 |
|---:|---|---|
| 0 | 初始化 | 模块和平台初始化参数 |
| 1 | 应用输入/事件 | 事件号及参数 |
| 2 | 计时器分发 | 计时器或回调参数 |
| 3 | 停止/退出 | 清理上下文 |
| 4 | 暂停 | 生命周期通知 |
| 5 | 恢复 | 生命周期通知 |

消息码 0 至 5 在常见 SDK 中稳定；具体 input 布局和扩展消息应按模块/SDK 探测，不能把某个包的私有消息推广成通用 ABI。

## 模块参数块

常见 32 位 ABI 在登记 helper 时建立至少 20 字节的参数块：

| 偏移 | 大小 | 字段 | 作用 |
|---:|---:|---|---|
| `+0x00` | 4 | RW base | 模块可写/静态数据基址，通常也是进入模块时的 R9 值 |
| `+0x04` | 4 | RW length | RW 区长度 |
| `+0x08` | 4 | EXT type | 模块类型，具体枚举随 SDK/loader 变化 |
| `+0x0C` | 4 | module/extChunk | 模块或 loader 上下文的 guest 地址 |
| `+0x10` | 4 | stack field | 栈相关字段，精确语义随 loader 变化 |

字段宽度以 32 位 guest ABI 为准。宿主在读取任何地址或长度前必须做映射范围检查。

**证据：稳定 SDK ABI（前四项的交换作用）；有限样本观察（类型枚举和栈字段细义）。**

## `game.ext` 与嵌套模块

大型应用常把 `cfunction.ext` 作为包装/装载层，再加载 `game.ext`、`graphics.ext`、支付、浏览器或资源下载模块。有的应用还从主包打开嵌套 MRP，或让子 EXT 再登记自己的 helper。

这些模块不能共享一个隐式全局 RW 基址：wrapper、主游戏和前台子模块可能各有独立 R9、参数块、栈与生命周期。一次跨模块调用至少需要保存：

- 当前模块身份；
- ARM/Thumb 执行状态；
- 返回地址和栈；
- R9 静态基址，以及工具链需要的其他持久寄存器；
- 当前平台表/回调上下文。

返回后应恢复调用者上下文。具体 loader 的私有 chunk 布局、固定加载地址和针对单个程序的调度补丁，不属于通用 MRP 规范。

**证据：多样本验证与版本/平台相关。**

## 生命周期和事件循环

公共 MRC 应用接口常以如下生命周期出现：

```text
mrc_init()
mrc_event(code, param0, param1)
mrc_pause()
mrc_resume()
mrc_exitApp()
```

宿主收到按键、触摸、菜单、网络或系统消息后，将其规范化为 MRP 事件，再通过 MR 层或 helper code 1 送给应用。计时器到期通常通过 helper code 2 分发。网络、DNS、编辑框和短信等平台操作可能先返回等待状态，稍后再产生事件或回调，因此运行时不能假设平台调用都同步完成。

建议的状态约束：

| 状态 | 可接受操作 | 关键约束 |
|---|---|---|
| Loaded | 初始化、卸载 | 尚不能投递普通输入 |
| Running | 事件、计时器、平台回调、加载子模块 | 同一 guest 上下文的重入策略必须明确 |
| Paused | 恢复、退出、必要的系统结果 | 应暂停或抑制应用计时器，具体策略按 SDK |
| Stopping | 清理和待完成回调的取消 | 不再创建新异步操作 |
| Stopped | 无 | helper 和 guest 地址均不可再调用 |

退出清理顺序通常从前台子模块开始，逆向释放到 wrapper 和 MR VM。即使初始化只完成一部分，也必须能沿相同所有权关系回收资源。

**证据：稳定 SDK ABI（生命周期入口与消息）；版本/平台相关（暂停计时器和异步重入细节）。**
