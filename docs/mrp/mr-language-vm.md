# MR 语言与虚拟机

MRP 的应用层包含一种 Lua 家族的动态语言，本文简称 **MR 语言**。它沿用 Lua 5.0 时代的主要语义模型，但文本关键字、二进制签名、版本范围、标准库和平台绑定均有 Mythroad 特征。因此，“Lua 家族”是用于理解语言原理的分类，不表示普通 Lua 解释器可以直接运行所有 `start.mr`。

本文只记录实现互操作所需的外部格式和行为。词法分析算法、语法树表示、指令分发写法、垃圾回收器结构、错误文本以及宿主对象设计，都不是 MRP 格式所要求的内容。

## 两种输入形态

MR 运行时面对的入口内容有两种形态：

| 形态 | 识别方式 | 处理过程 |
|---|---|---|
| 文本 MR | 不具有二进制 chunk 签名 | 解码字节流，完成词法和语法分析，生成函数原型与 VM 指令 |
| 预编译 MR | 以完整的 MR chunk 签名开始 | 校验头部、版本和数据布局，直接重建函数原型与 VM 指令 |

两条路径最终产生相同类别的可执行对象，然后由同一套 VM 执行。文件名不能决定内容形态：`start.mr` 既可能是文本，也可能是预编译 chunk；gzip 只是 MRP 容器层的存储方式，解压之后仍需再次识别 MR 内容。

```text
MRP 目录项
  -> 读取受限范围内的 payload
  -> 可选的 gzip 解压
  -> MR 内容识别
       -> 文本：词法分析 -> 语法分析 -> 指令生成
       -> 二进制：chunk 校验 -> 函数原型重建
  -> 创建顶层闭包
  -> VM 执行入口
```

**证据：稳定 SDK ABI（双输入路径）；版本/平台相关（文本编码和可接受的 chunk 版本）。**

## 文本方言

MR 文本在作用域、表、闭包、函数调用、条件、循环和协程等概念上接近早期 Lua，但存在可观察的词法差异。常见方言使用：

| MR 写法 | 概念 | 常见标准 Lua 写法 |
|---|---|---|
| `def` | 定义函数 | `function` |
| `elif` | 条件的后续分支 | `elseif` |
| `&&` | 逻辑与 | `and` |
| `||` | 逻辑或 | `or` |
| `!` | 逻辑非 | `not` |
| `!=` | 不等 | `~=` |
| `..` | 字符串连接 | `..` |

常见控制词还包括 `local`、`if`、`then`、`else`、`end`、`while`、`repeat`、`until`、`for`、`in`、`break` 和 `return`。这些差异意味着直接交给现代 Lua 解析器通常会在合法 MR 源码上报语法错误；简单替换关键字也不足以证明兼容，因为优先级、调试信息、变参和边界行为仍与 chunk/VM 版本相关。

源文件的字节编码与运行时字符串编码也应分开处理。老应用常把非 ASCII 文本保存为本地编码，语言关键字本身是 ASCII。实现不应在词法分析前无条件把整个输入转为 UTF-8，否则可能改变字符串常量的原始字节。

**证据：稳定 SDK ABI（关键字和运算符）；版本/平台相关（字符编码与语法细节）。**

## 预编译 chunk

已知 MR 二进制 chunk 以四个字节开始：

```text
1B 4D 52 50
```

它们分别表示 ESC 和 ASCII `MRP`。这与 MRP 容器开头的 ASCII `MRPG` 是两个不同层次的签名：前者识别包内的 MR 字节码，后者识别整个归档文件。

签名后常见一个版本字节和一个字节序标记。已知 SDK 家族使用的版本范围为 `0x50` 至 `0x80`；这表示可观察的格式世代，不应被解释为十进制版本号或现代 Lua 版本号。`0x50` 形态还携带整数、长度、指令字段和 number 表示的尺寸/格式描述，较新形态采用不同的精简头部约定。

函数原型在概念上包含：

- 来源和行号信息；
- 固定参数数目、变参标记和所需寄存器数；
- 局部变量及其有效指令区间；
- upvalue 描述；
- nil、number、字符串等常量；
- 嵌套函数原型；
- VM 指令序列。

调试字段可以为空，不能作为执行的必要条件。所有数量、字符串长度、嵌套深度和指令数量都来自不可信输入，分配之前必须做上限、乘法和文件余量检查。

仅检查首字节 `0x1B` 不足以确认 chunk。实现应校验完整签名，并在支持表中精确匹配版本；未知版本应拒绝或交给明确的兼容模块，而不是按最接近版本猜测。

**证据：稳定 SDK ABI（签名与结构类别）；版本/平台相关（版本范围内的字段布局）。**

## 指令模型

已知 MR VM 使用 32 位定长指令和寄存器式执行模型。常见指令字的字段为：

```text
31              24 23          15 14           6 5        0
+----------------+---------------+---------------+----------+
| A: 8 bits      | B: 9 bits     | C: 9 bits     | OP: 6    |
+----------------+---------------+---------------+----------+
```

另两种解释会把 B 与 C 合并为 18 位无符号 `Bx`，或以偏置形式解释为有符号 `sBx`。字段宽度和位置是字节码兼容事实；如何在 Rust/C 中解码、是否预解码、是否使用 JIT，均属于实现选择。

指令语义覆盖以下类别：

- 常量、全局、局部寄存器和 upvalue 的读写；
- 表的读取、写入和构造；
- 算术、连接、比较和条件跳转；
- 函数调用、尾调用、返回和闭包创建；
- 数值循环、迭代循环以及变参；
- 由 SDK 版本提供的附加操作。

兼容器必须按 chunk 对应的 opcode 表解释指令，不能仅凭字段布局把未知 opcode 当作空操作。跳转目标、常量索引、寄存器范围、嵌套原型索引和 upvalue 索引都应在执行前或执行时验证。

**证据：稳定 SDK ABI（32 位字段布局）；版本/平台相关（完整 opcode 集合及附加操作）。**

## 值、调用与内存

MR 的常见运行时值包括 nil、布尔值、number、字符串、表、函数、userdata 和线程/协程。函数可以是 MR 闭包，也可以是运行时登记的平台函数。调用边界使用 VM 栈和结果数量约定，不等同于 ARM 的 R0-R3 调用约定；只有进入 EXT 后才切换到 [ARM ABI](arm-abi.md)。

常见 SDK 以双精度浮点数表示 number。双精度可以精确表示一定范围内的整数，但它不是宿主指针类型。尤其在 64 位宿主上，不应借助 number 往返传递宿主地址；对旧 API 暴露的地址类数值，应使用受检查的 32 位 guest 地址或宿主管理的句柄。

字符串是带显式长度的字节序列，不能假设内容为 UTF-8，也不能用第一个 NUL 判断 VM 字符串结束。只有调用要求 C 字符串的平台接口时，才需要生成有边界的临时终止形式。

表、闭包、字符串和 userdata 的回收时机不是包格式的一部分。实现可以使用不同 GC 算法，但必须保持可观察的生命周期要求，例如闭包持有 upvalue、活动调用帧中的值存活，以及退出后不再回调已释放对象。

**证据：常见语言语义；32 位地址边界为稳定 SDK ABI。**

## 标准库与平台绑定

MR VM 通常提供基础、字符串、表、文件和网络等库，并额外登记绘图、声音、计时器、设备信息、资源读取和 native EXT 装载能力。库名、函数名、参数顺序、返回值和错误行为是应用可观察接口；宿主如何实现窗口、文件系统、网络和音频不是语言规范的一部分。

普通 Lua 标准库不是完整替代品。兼容实现应按目标 SDK 建立能力清单，至少区分：

- Lua 家族共有的语言/库语义；
- Mythroad 修改过的名称或参数；
- MRP 平台专用能力；
- 某个 SDK 或厂商才有的扩展；
- 因安全策略而明确不可用的外部副作用。

平台不支持某项能力时应返回该 ABI 允许的失败或等待结果，不能伪造成功。涉及短信、呼叫、联网和宿主文件的操作还需要宿主侧授权，但授权流程不应改变 guest 看到的函数签名。

**证据：稳定 SDK ABI（库绑定机制）；版本/平台相关（具体库集合）。**

## `start.mr` 与生命周期

默认入口 `start.mr` 的顶层代码先执行一次，用于初始化状态、装载资源和定义后续回调。常见 MR 应用通过全局函数接收运行时消息：

| 名称 | 常见用途 | 常见参数 |
|---|---|---|
| `dealevent` | 按键、触摸和系统事件 | 事件号、参数 0、参数 1 |
| `dealtimer` | 应用计时器到期 | SDK/应用约定的计时信息 |
| `suspend` | 应用进入暂停状态 | 通常无参数 |
| `resume` | 应用从暂停状态恢复 | 通常无参数 |

这些名称是常见应用约定，不表示每个包都必须全部定义。没有对应函数时，运行时可以忽略该层通知、使用 native 路径，或按目标 SDK 的规则处理。若 `start.mr` 装载 `cfunction.ext`，MR 回调还可能充当事件到 native helper 的桥接层；事件所有权应由目标 SDK 协议决定，避免 MR 和 EXT 重复消费同一消息。

完整启动和退出次序见 [MRP 启动与执行模型](execution-model.md)，事件编号见 [事件、按键与公共值](events-and-values.md)。

**证据：多样本验证（回调名称）；版本/平台相关（缺省行为与 MR/native 路由）。**

## 与具体实现分离

为了实现互操作，新的运行时需要复现的是输入和输出契约，而不是某份既有代码的内部构造：

| 兼容所需事实 | 可独立选择的实现方式 |
|---|---|
| MR 文本的 token、语法和可观察求值规则 | 手写解析器、解析器生成器或其他经过验证的前端 |
| chunk 签名、版本、字段宽度与字节序 | 流式读取、零拷贝视图或拥有所有权的数据结构 |
| opcode 编号、操作数字段和指令效果 | switch、分发表、预解码器、解释器或 JIT |
| 值类型、作用域、闭包和调用结果 | 任意满足语义的 Rust/C 数据模型 |
| 标准库及 MRP 平台 API 的外部行为 | 不同的窗口、文件、网络、音频和调度后端 |
| 生命周期回调和 MR/EXT 消息边界 | 不同的状态机、任务队列和模块所有权设计 |

独立实现不应复制既有项目的源文件组织、函数拆分、变量命名、注释、错误字符串或非必要控制流。更稳妥的工程流程是为每条兼容需求记录二进制样本或公开接口证据，由未接触既有实现表达的开发者依据本类功能规格编写代码，并使用独立生成的测试验证行为。

本文的文字、表格和示意均为针对互操作事实的新表述，没有纳入现有运行时的实现代码。
