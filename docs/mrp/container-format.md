# MRP 容器格式

MRP 是带有固定头部、文件目录和数据记录的归档格式。数值字段通常按 32 位无符号整数解释；除明确标出的副本外，常见包使用小端序。解析器必须把包视为不可信输入，不能依靠 C 结构体直接映射文件。

## 总体布局

常见的 240 字节头部包可以表示为：

```text
0x00000000  固定/扩展头部
ListStart   目录项序列
FileStart   目录尾部相关值
FileStart+8 第一条数据记录
...         其余数据记录
FileLen     文件结束
```

`FileStart` 这个历史字段名容易造成误解。文件中偏移 `0x04` 保存的值还要加 `8`，才是常见包中第一条数据记录的起点。目录项本身给出的 payload 偏移可以直接定位文件内容，所以兼容读取器通常不需要顺序扫描数据记录。

**证据：多样本验证。** 240 字节头部和 `FileStart + 8` 关系在多份包中一致；扩展头和工具链变体仍需依照 `ListStart` 而不是硬编码 `0xF0`。

## 头部字段

| 偏移 | 大小 | 字节序 | 含义 | 兼容性说明 |
|---:|---:|---|---|---|
| `0x00` | 4 | - | ASCII `MRPG` | 必须先验证魔数 |
| `0x04` | 4 | 小端 | 目录尾部相关值 `FileStart` | 常见数据记录起点为该值加 8 |
| `0x08` | 4 | 小端 | 包总长度 `FileLen` | 应与实际文件范围交叉验证 |
| `0x0C` | 4 | 小端 | 目录起点 `ListStart` | 常见值为 `0xF0`，但不可硬编码 |
| `0x10` | 12 | 字节串 | 包内文件名 | 固定宽度，NUL 终止不应强制假设 |
| `0x1C` | 24 | 字节串 | 显示名称 | 老包常用本地中文编码 |
| `0x34` | 16 | 字节串 | 认证/构建字段 | 精确语义随工具链变化 |
| `0x44` | 4 | 小端 | 应用 ID | 与 `0xC0` 的大端副本对应 |
| `0x48` | 4 | 小端 | 版本号 | 与 `0xC4` 的大端副本对应 |
| `0x4C` | 4 | 小端 | 标志 | 可见性、CPU、shell 等位的解释随构建器变化 |
| `0x50` | 4 | 小端 | 构建/格式常量 | 观察包中常见 `10002` |
| `0x54` | 4 | - | 保留或变体字段 | 不应要求为零 |
| `0x58` | 40 | 字节串 | 厂商名称 | 固定宽度 |
| `0x80` | 64 | 字节串 | 描述 | 固定宽度 |
| `0xC0` | 4 | 大端 | 应用 ID 副本 | 可用于一致性检查，不宜盲目信任 |
| `0xC4` | 4 | 大端 | 版本号副本 | 可用于一致性检查，不宜盲目信任 |
| `0xC8` | 4 | - | 保留 | 版本/平台相关 |
| `0xCC` | 2 | 小端 | 目标屏幕宽度 | 允许为零 |
| `0xCE` | 2 | 小端 | 目标屏幕高度 | 允许为零 |
| `0xD0` | 1 | - | 平台标识 | 常见构建器用 1 表示 MTK/MStar、2 表示 Spreadtrum、0 表示其他 |
| `0xD1` | 31 | - | 保留 | 形成常见的 240 字节头部 |

**证据：多样本验证与版本/平台相关。** 字段边界稳定；认证字段、标志位和平台值的业务解释并非所有 SDK 都相同。

## 目录项

目录从 `ListStart` 开始，由变长项连续组成：

```text
u32le name_len
u8     name[name_len]
u32le payload_offset
u32le stored_length
u32le reserved
```

单项字节数为 `4 + name_len + 12`。常见工具把文件名末尾的 NUL 算入 `name_len`，但安全解析器应当按长度读取，然后只在确有 NUL 时去除一个终止字节。`payload_offset` 指向 payload 的第一个字节；`stored_length` 是包内保存长度，压缩时不是解压后长度。最后的 32 位字段在观察样本中通常为零，其含义应视为保留。

目录的停止位置应由头部范围关系推导，并同时验证：

```text
ListStart <= next_entry <= FileStart + 8 <= actual_file_size
payload_offset + stored_length <= min(FileLen, actual_file_size)
```

所有加法都应使用不会溢出的检查。`name_len`、条目数、单文件长度和解压后长度应设置实现上限。

**证据：稳定 SDK ABI。** 目录项的字段顺序和 payload 定位是读取现有包所需的互操作格式。

## 数据记录

历史打包器为每个文件写入如下记录：

```text
u32le name_len
u8     name[name_len]
u32le stored_length
u8     payload[stored_length]
```

目录中的 `payload_offset` 跳过记录前面的名称和长度，直接指向 `payload`。数据记录里的名称和长度可以用于诊断或一致性校验，但目录仍是随机访问的主要索引。

**证据：多样本验证。** 不同构建器可能加入扩展数据，读取器不应仅靠顺序记录重建目录。

## 压缩识别

payload 以 `1F 8B 08` 开头时，常见语义是 gzip 数据。没有这个签名的文件可直接是未压缩数据，包括 `start.mr`、图片或 EXT。目录只保存包内长度，gzip 流中的原始长度字段不能代替安全的解压上限，因为它只有 32 位且不构成资源承诺。

推荐流程：

1. 对目录范围和保存长度完成校验。
2. 只读取该条目声明的字节范围。
3. 检测 gzip 签名；若匹配则使用有输出上限的流式解压。
4. 检查流完整结束，拒绝截断或超出上限的输出。
5. 将“包内保存长度”和“解压后长度”作为两个独立属性保留。

**证据：常见约定。** gzip 很普遍，但 MRP 并不要求每一项都压缩。

## 重名与查找

实际包可能出现重复文件名，甚至出现多个 `start.mr`。因此目录模型应保留原始顺序和全部条目，不要在解析阶段直接塞入会覆盖旧值的 map。究竟选择第一个、最后一个还是由更高层入口参数选择，属于运行时/SDK 版本行为。

文件名还可能来自旧式字符编码，并可能包含大小写差异。兼容层应把原始字节名与用于 UI 的解码字符串分开。

**证据：多样本验证；查找优先级为版本/平台相关。**
